# `.b16` cartridges: philosophy, structure and limits

Italian version: [B16-IT.md](B16-IT.md).

> **Status:** design document. The bm profile is decided (§0, 2026-10-05) but not yet
> implemented; the rest is the design of the container. Today's `.bm` cartridges do not
> change.
>
> **Name (user's decision, 2026-10-04):** the format is called **`.b16`** (formerly
> `.s16`): the **limited-resource cartridge for handheld consoles**, starting with the
> RGB30, where the menu looks for them in `bm/`. To be developed further later.

## 0. The bm profile, version 1 (user's decisions, 2026-10-05)

A limited environment **like PICO-8**: a machine with fixed numbers, the same on the Pi and
on the RGB30 (tuned to the slower one, the Pi Zero), so a `.b16` runs the same way everywhere.
These decisions come before the rest of the document: where they contradict it, this section
wins (the differences are stated point by point).

- **Container**: the **same as `.bm`** (`BMCART`, the sections of `src/bm/bm.h`), with a
  field that states the profile (`b16` version 1) and the `.b16` extension. SDK, tools and
  Market work right away. The new container of §3 (`B16CART`) will be made only if a game
  needs it; the banks of §4 become sections of today's container.
- **Screen**: **360×360** or **720×720**, written in the file and fixed for the whole session
  (no `screen()`). 360 is exactly ×2 on the RGB30's 720×720 panel (320 would be ×2.25);
  on the Pi the square sits in the middle of the TV, as Yharnam does today. (Different from
  §2.6, which wanted a single resolution: two declared sizes, never changed during play.)
- **Colors**: a palette of **256 colors** (24 bit) per game, indexed graphics (like
  Yharnam's SHEET8).
- **Fixed memory**: Lua **4 MiB**; resident graphics one **1024×1024** pixel bank at a time
  (the file has as many as it likes, the game switches them between one scene and the next,
  §4); map up to 8 levels and a world up to 8×8 screens (§5.2); sound **8 voices**; save
  **64 KiB**.
- **Fixed CPU**: a per-frame budget of Lua instructions (Pi and RGB30 have the same
  interpreter: they count the same) plus a **fixed cost for every draw** (pixels, sprites,
  triangles). The game runs at **60 fps** and, if a frame goes over the budget, **drops by
  itself to 30** (like PICO-8), the same on both consoles; the dev kit shows the CPU as a
  percentage. The number is tuned with a test on the Pi. (Different from §6.4, where the
  budget was only a guard against infinite loops: with a single interpreter it becomes the
  real limit.)
- **3D**: allowed, with a cap on triangles per frame that counts toward the CPU (Overbit
  `.b16`, M41).
- **Controls**: a SNES-style pad (d-pad, A B X Y, L R, Start Select) plus a stick, the same
  with the DS4, the RGB30 buttons and the keyboard (more than the 5 bits of §6.6).
- **Sandbox**: no files (`cart_*`, `ls`), fixed screen; `rnd()` with a seed, so a session
  can be replayed identically (§2.9: randomness stays deterministic); network and
  `report()` with the question to the player, as for `.bm`.
- **Cap**: **8 MiB** for the file (§5.1). **No token limit** (§2.4): the real limits are
  CPU and memory.
- **Where they show up**: the Pi shows `.bm` and `.b16` (they run the same way); the RGB30
  only `.b16` (user's choice), in its Market too.
- **Yharnam** is the first candidate: it already fits for file (5.7 MiB) and code (455 KB).
  **360×360 screen: done (2026-10-10, `--res 360x360`, branch `yharnam-update`)**. **The
  graphics banks are not, and for Yharnam they are neither needed nor enough** (measurements
  from 2026-10-10 on the 4096×3392 sheet, 13.9 Mpx, 41 MiB expanded): the hunter alone is
  4.4 Mpx (four times a 1024×1024 bank, and it is visible in every frame), the four bosses
  5.9 Mpx, the small creatures 2.5, tiles and objects 1.1. A bank that holds "everything
  that is seen together" (§4.2) therefore does not exist for Yharnam without redrawing the
  hunter smaller. Switching bank per area (one bank per boss, loaded near the arena) would
  free at best 15 MiB of the Pi Zero W's 447 MiB of heap (3%), does not change the cost of a
  frame (a blit costs the same from a small or a large sheet) and adds a synchronous
  conversion (about 1.5 Mpx, to be measured on the console) exactly where the game is most
  tense. It is not done until the console's measurements (the dev kit session report) show
  that memory or loading are a problem.

This document collects the idea of the **`.b16`** cartridge: a single file that contains a
whole game and that the machine loads only one piece at a time. It describes the
*container* (what it is, how it is made, what rules and limits it has) and the *contract*
between cartridge and system. It does not describe the machine that runs the game
(processor, graphics, audio): that will be defined by the project that adopts the format,
in a **machine profile** (§7).

## 1. The idea in brief

- A cartridge is **a single binary file**, extension `.b16`, for every game size.
- The file has a **fixed header** (identity, integrity) and a **section table** that
  describes everything else: code, map banks, graphics banks, palette, and other things in
  the future.
- Large contents are split into fixed-size **banks**. The cartridge on disk can be much
  larger than the machine's memory: what stays in memory is **one bank per type at a
  time**, and the game chooses which by writing its number.
- The limits are **few, sharp and chosen on purpose**: a byte cap for the whole file,
  *maximums* for what the cartridge declares, a per-tick execution budget against
  infinite loops. No fake limits (no token count).
- The cartridge has a **stable identity** (uid) and an **integrity** check (CRC-32);
  there is reserved room for a cryptographic hash, for future authenticity.

## 2. Principles

Every rule of the format derives from one of these principles. When a future decision is
not covered by the document, it must be made starting again from here.

### 2.1 One file, one extension, one format

A single extension for all sizes. The idea of different extensions per size
(`.s1`, `.s2`, ...) was discarded: the structure (how many banks, how big each one is)
already lives in the header, and the file name must not repeat it.

### 2.2 The file describes itself, without duplicated data

A reader must be able to understand the file by reading only the header and the section
table: how many sections, of what type, where they start, how many banks, how big each one
is. Every piece of information appears **only once**: the total size of the cartridge, for
example, **is not a field**, it is derived from the sections. A value written twice sooner
or later becomes two different values.

### 2.3 The cartridge is larger than the active memory

A large cartridge does **not** mean that all its content must be in memory at the same
time. Cartridge consoles worked this way: the SNES had 64 KiB of video memory with
cartridges up to 6 MiB, and the game copied into memory only the graphics of the current
scene, replacing them on level changes.

`.b16` does the same: the file contains **N banks** of each type, the machine keeps
**one resident** per type, and the exchange (swap) is an explicit operation of the game
(§4). The machine's memory stays small and fixed; the cartridge grows without touching
it.

### 2.4 Few, sharp, real limits

Two opposite mistakes to avoid:

- **fake limits**: a token count on the source limits the *length of the text*, not
  performance (a loop of 1000 iterations costs the same tokens as the body written once).
  It adds complexity without real guarantees. `.b16` does not count tokens;
- **no limit**: without a clear cap the format becomes vague and every implementation
  decides on its own.

The chosen way: a **byte cap** for the whole file (§5.1), **maximums** for the declared
quantities (§2.5), a **per-tick budget** that stops infinite loops (§6.4). The performance
constraint stays the natural one: how much work the game manages to do in one tick.

### 2.5 Maximums, not fixed values

A machine limit is a **ceiling**, not a value equal for all cartridges. Example: the game
world has a maximum (8×8 screens, §5.2), but a cartridge can declare a smaller one, and
the game behaves according to the **declared** size (scrolling wraps at the edges of the
real world, not of the maximum).

Two precise consequences:

- per-cartridge quantities live **in the file** (in the section table), read at load
  time;
- the **machine's memory is always sized to the maximum**: the position of its regions
  never moves, whether the cartridge is small or large. If a per-cartridge size moved the
  addresses of everything after it, two implementations would end up diverging silently
  (§9.2).

### 2.6 A single machine, no alternative modes

The header offers no alternative modes (a second resolution, a second screen format,
...). A mode planned "for the future" and never really used becomes debt: a field to
read, a case to handle, space reserved everywhere. If the machine changes, the format
version will change.

### 2.7 Stable identity, integrity, authenticity

- **Identity**: a 16-byte `uid` is born with the cartridge and never changes for its whole
  life, through edits and repackaging. It is its serial number: the natural key for saves,
  records, external registries.
- **Integrity**: a CRC-32 of the content detects accidental corruption (interrupted copy,
  faulty SD). A cartridge with a wrong CRC is rejected.
- **Authenticity**: 32 bytes reserved for a SHA-256. It will be needed if and when an
  external registry of "original" cartridges exists (distribution, exchange, credit to the
  authors; NFTs were also mentioned in the past). The format **prepares** the place so as
  not to break in the future; the engine stays **agnostic**: registries, markets and
  verifications live outside the engine and are not designed. Until it is needed, the field
  is all zero.

### 2.8 Content and computation are different things

Banks give **more content** (assets). Any **computation** extensions that a cartridge
carries with it (the equivalent of coprocessors in old cartridges) are an **orthogonal**
concept: they do not compete for the same space and must not be mixed into the bank
mechanism. No computation extension is designed.

### 2.9 Determinism

Same cartridge + same input sequence = **same bytes in memory and same pixels on screen,
tick by tick**, on any implementation. For this reason the cartridge has no access to
external sources: no random numbers from the system, no clock, no files or network
(§6.3). Whoever wants randomness writes their own generator, seeded by the game itself
(for example from the ticks elapsed before a key is pressed).

### 2.10 Growing without breaking

- Every reserved byte is written as **zero**.
- Every new field is born in a reserved space, and every assignment of reserved bytes is
  **recorded** in the specification (who uses it, with which values) before implementing
  it: otherwise two independent proposals may want the same byte.
- Unknown section types are provided for by the format: an old reader skips the optional
  ones and rejects those marked essential (§3.4).
- An incompatible change raises `version`.

### 2.11 Source and cartridge use the same bytes

The working folder of a cartridge (§8.1) contains one file per bank **in the same binary
format** it will have inside the cartridge. Packing = writing header and table, then
appending the banks. No conversion, no intermediate format to keep aligned.

### 2.12 Honesty

A function that does not exist yet says so; it does not pretend to work. An editor can be
ahead of the engine (prepare data that the engine does not use yet), but must never make
anyone believe the engine uses them. A failed start or a crash is shown **on the
screen**, with the reason (§6.5).

## 3. File structure

All integers are **little endian**. Offsets are counted from the start of the file. Every
field sits at an offset that is a **multiple of its own size** (u16 at even offsets, u32
at multiples of 4): the layout is fixed by this table, not by how a compiler lays out a
structure (§9.1).

```
offset 0        +-------------------------------+
                | header (256 bytes)            |
offset 256      +-------------------------------+
                | section table                 |
                | section_count × 24 bytes      |
                +-------------------------------+
                | zeros up to a multiple of 16  |
                +-------------------------------+
                | CODE  (1 bank)                |
                | MAP   bank 0, 1, ... N-1      |
                | GFX   bank 0, 1, ... M-1      |
                | PAL   (optional)              |
                | ICON  (optional)              |
                | ... future sections           |
end of file     +-------------------------------+
```

### 3.1 Header (version 1, 256 bytes)

| Offset | Type | Field | Notes |
|---|---|---|---|
| 0 | char[8] | `magic` | `"B16CART"` followed by a 0 byte |
| 8 | u16 | `version` | 1 |
| 10 | u16 | `header_size` | 256; the section table starts here |
| 12 | u16 | `section_count` | number of entries in the table |
| 14 | u8 | `code_type` | language of the `CODE` section (§3.5) |
| 15 | u8 | `flags` | reserved, 0 |
| 16 | u8[16] | `uid` | identity of the cartridge (§2.7), UUID v4 |
| 32 | char[64] | `title` | UTF-8, zero-terminated (at most 63 bytes of text) |
| 96 | char[32] | `author` | UTF-8, zero-terminated (at most 31 bytes of text) |
| 128 | u32 | `created_unix` | creation date, Unix seconds (good until 2106) |
| 132 | u32 | `content_crc32` | CRC-32 from `header_size` to the end of the file (§3.6) |
| 136 | u8[32] | `content_sha256` | reserved, all zero until used (§3.6) |
| 168 | u8[88] | `reserved` | zero |

`header_size` is written in the file so that a future version can lengthen the header:
a reader always finds the section table at `header_size`.

### 3.2 Section table

`section_count` entries of **24 bytes**, one per section type:

| Offset | Type | Field | Notes |
|---|---|---|---|
| 0 | char[4] | `type` | four-character code, e.g. `"CODE"`, `"MAP "` |
| 4 | u32 | `offset` | start of bank 0, multiple of 16 |
| 8 | u32 | `bank_size` | bytes of **each** bank of the section |
| 12 | u16 | `bank_count` | number of banks (indices from 0 to `bank_count`−1) |
| 14 | u16 | `flags` | bit 0 = **essential** (§3.4); other bits 0 |
| 16 | u16 | `param0` | meaning defined by the type |
| 18 | u16 | `param1` | meaning defined by the type |
| 20 | u32 | `reserved` | zero |

The banks of a section are contiguous: bank *n* starts at
`offset + n × bank_size`. Between one section and the next there are only alignment
zeros (fewer than 16 bytes).

### 3.3 Section types (version 1)

| Type | Banks | Essential | Content | `param0` / `param1` |
|---|---|---|---|---|
| `CODE` | exactly 1 | yes | the game program (§3.5); `bank_size` = its length | 0 / 0 |
| `MAP ` | 1 or more | yes | level maps ("stages"): one bank = the map of one world | width / height of the world in screens (1..maximum, §5.2) |
| `GFX ` | 1 or more | yes | graphics banks: all the tiles/sprites usable in a scene | 0 / 0 |
| `PAL ` | 1 | yes | initial palette, copied into memory at installation | 0 / 0 |
| `ICON` | 1 | no | image of the cartridge for the menu (§8.4) | width / height in pixels |
| `SFX `, `MUS ` | — | — | **reserved** for future audio banks (§10) | — |

Rules:

- `CODE` is always there, exactly once. The others are optional; each type appears at most
  once.
- The **internal** format of a bank (what a map cell, a tile, a color looks like) is
  **not** the container's business: the machine profile defines it (§7). The container
  only knows the type, number and size of the banks.
- Within a section all banks have the **same size**. For `MAP ` the size derives from the
  declared world (`param0` × `param1` screens): a small world takes little space in the
  file, but in memory it is always installed in the same region, sized to the maximum
  (§2.5). `bank_size` is still written in the entry, so that a reader that does not know
  the type can skip the section; the reader that knows it checks that it matches what the
  profile derives from the parameters.

### 3.4 Unknown and essential sections

A reader that finds a type it does not know:

- if the **essential** bit is 0, **ignores** the section (e.g. an icon in a new format:
  the game runs anyway);
- if it is 1, **rejects** the cartridge with a clear message ("requires a newer
  version"), instead of running it halfway.

This way new types (audio, game data, ...) are added without raising `version`, and
without an old system running a new cartridge badly.

### 3.5 `code_type`

| Value | Meaning |
|---|---|
| 0 | invalid (a header zeroed by mistake must not look like a cartridge) |
| 1 | Lua source in UTF-8 (dialect fixed by the profile, §6.2) |
| 2–255 | reserved |

No precompiled bytecode: it is not portable across interpreter versions and, loaded as it
is, it allows bypassing the sandbox. The cartridge carries source.

### 3.6 Integrity and authenticity

- `content_crc32`: CRC-32 IEEE 802.3 (the same as zlib) of the bytes **from `header_size`
  to the end of the file**: section table, padding and all banks. The header is protected
  by the structure checks (§3.7). It is only for accidental corruption, it is **not** a
  guarantee of authenticity.
- `content_sha256` (when it is used): SHA-256 of the **whole file**, with the 32 bytes of
  the field itself taken as zero. It also covers uid, title and author: authenticity must
  bind the identity of the cartridge, not just its data.

### 3.7 Reader checks

In order; the first that fails stops loading with a message that names the reason, **on
the screen**:

1. file at least 256 bytes long; correct `magic`; supported `version`;
2. `header_size` ≥ 256; the table is inside the file;
3. for every entry: `offset` multiple of 16; all banks (`bank_count × bank_size`) inside
   the file; no overlap with the header, the table or other sections; no repeated type;
4. unknown types: essential → rejection, otherwise ignored (§3.4);
5. `CODE` present once; known `code_type`;
6. file size within the cap (§5.1);
7. `content_crc32` matches;
8. profile checks: size of every bank as expected, parameters within the maximums
   (§5.2), palette of the right size.

The writer (the packer) must guarantee the same rules **before** writing, plus: bank
indices dense from 0 (no gaps), every bank exactly `bank_size`, reserved fields and
padding zero.

## 4. Banks and swap

### 4.1 The mechanism

- For every banked type (`MAP `, `GFX `, audio in the future) the machine has **one
  resident region**, sized to the maximum of that type.
- The game selects a bank by writing its **number** (in Lua, for example, `stage(n)` for
  maps and `gfxbank(n)` for graphics). The machine copies bank *n* from the cartridge into
  the resident region.
- The swap is **synchronous and immediate**: when the call returns, the new bank is
  already in memory. No waiting, no asynchronous loading to handle.
- A **nonexistent** bank number **has no effect** (it is not an error, it is not a crash).
- At installation, **bank 0** of every type present is selected automatically.
- The resident region is normal memory: after the swap the game can modify it (e.g. open a
  door in the map). The change lives until a bank is selected again: **the cartridge is
  never written**.

### 4.2 Game units

- A **map bank** is a *stage*: a whole world, up to the maximum. A game is not limited to
  one world: it has as many as fit in the cartridge.
- A **graphics bank** is the graphics set of a scene: everything that is seen together
  must fit in one bank.
- Maps and graphics are chosen **independently**: the same graphics set can serve several
  stages, and vice versa.

### 4.3 Why copying and not direct access

Copying a whole bank when needed is simple to specify, identical on every implementation
and fast (a memory copy). Worlds larger than the maximum, if ever needed, would be done as
on real consoles: whole map outside the resident region, a **window** copied when
scrolling crosses an edge. It is a feature of its own, not an automatic consequence of how
large the map is, and today it is not planned.

## 5. Limits

### 5.1 Cartridge cap: 8 MiB

- The whole file (header + table + all sections) does not exceed **8 MiB**
  (8 388 608 bytes).
- Reference: the largest SNES cartridge (Star Ocean, 48 Mbit = 6 MiB). 8 MiB is just above
  it and has a clean binary value.
- It is not a header field: it is derived from the sections (§2.2). The packer checks it
  (refuses to write) and the reader checks it again.
- No rigid quota between code, maps and graphics: within the cap, the split is free
  (§10).

### 5.2 World: maximum 8×8 screens

- The world of a stage is a grid of screens, at most **8×8**, declared per cartridge in
  `param0`/`param1` of the `MAP ` section (from 1×1 to 8×8).
- Comparison: a typical SNES stage is 6–12 screens long in one direction; the PICO-8 map
  is 8×4 screens. 8×8 = 64 screens in a 2D grid is already generous, and there can be
  more than one world (§4.2).
- Scrolling **wraps** at the edges of the declared world, never at the maximum.

### 5.3 Other container limits

| Quantity | Limit | Where it comes from |
|---|---|---|
| Title | 63 bytes UTF-8 | 64-byte field with the final zero |
| Author | 31 bytes UTF-8 | 32-byte field with the final zero |
| Sections | one per type | §3.3 |
| Banks per section | 65 535 (u16), in practice set by the 8 MiB cap | `bank_count` |
| Resident banks | one per type at a time | §4.1 |
| Code | one section, source | §3.5 |
| Date | until 2106 | `created_unix` u32 |

### 5.4 Execution limits

Summarized here, described in §6:

- per-tick work budget: a guard against infinite loops, not a performance measure;
- no access to files, network, clock, system random numbers;
- players: up to **8**;
- errors and exceeding the budget are a crash: the cartridge closes, the system goes back
  to the menu.

## 6. Execution contract

### 6.1 Life cycle

1. **Loading**: checks of §3.7.
2. **Installation**: machine memory all zero (clean state), initial palette copied if the
   `PAL ` section is there, bank 0 selected for every banked type.
3. **Start**: the top-level code is run once; then, if defined, `_init()` once.
4. **Tick** (60 per second, reference value): the system writes the input of every player,
   calls `_update()`, then the machine produces the image and audio of the tick.
5. Between one tick and the next **the state persists** (global variables and captured
   locals, machine memory): `_update()` does not restart from zero.

### 6.2 Language

- `code_type` = 1: Lua, in **a single dialect** fixed by the profile (e.g. Lua 5.4).
- If several implementations with different interpreters must run the same cartridge, the
  allowed dialect is the **common part** between the versions, written in the
  specification (operators, integers/floats, libraries): a cartridge must not depend on
  where the versions differ.

### 6.3 Sandbox

- The cartridge's environment is built **from empty**, adding only what the specification
  lists (allow list). One does not start from the host's global environment and then
  remove pieces (deny list): a new host function must not become visible by mistake.
- Visible (reference): `assert error ipairs next pairs pcall select tonumber tostring
  type unpack xpcall`, the libraries `math string table coroutine`, the bit operations,
  the machine API.
- **Never** visible: `io os require load loadstring dofile debug collectgarbage print`.
- **Excluded** `math.random` and `math.randomseed`: system randomness breaks determinism
  (§2.9).
- Named constants (screen size, number of sprites, ...) exposed as globals **read from the
  real machine**, never copied by hand into the code: a number written by hand in the game
  breaks at the first change of the machine.

### 6.4 Per-tick budget

- An interpreter instruction counter (count hook) stops any execution that exceeds the
  budget. Reference value: 1 000 000 instructions per tick.
- It is a **guard against infinite loops**, not a performance measure: different
  interpreters do not count the same way. A correct game stays well below it.
- It applies **everywhere** cartridge code runs, not only to `_update()`:
  - to the top-level code and to `_init()` (an infinite loop there, without protection,
    blocks the whole system instead of giving a recoverable crash);
  - **to every coroutine** created by the cartridge: the main thread's hook does not
    propagate by itself to coroutines; `coroutine.create`, `resume` and `wrap` must be
    wrapped to arm the same hook, also on coroutines created outside a tick and resumed
    inside a later one;
  - with a JIT-compiling interpreter, the hook **does not fire** inside compiled code:
    compilation must be disabled for the cartridge's code.

### 6.5 Crash

- A Lua error (at load time, in `_init()` or in `_update()`) or exceeding the budget is a
  **crash**.
- The cartridge is stopped, the system goes back to the menu and shows **on the screen**
  the name of the cartridge and the reason. An immediate crash without a message looks like
  a "doesn't start".
- The state of a cartridge that crashed **is not reused** (no resume).
- A broken cartridge must never block the system.

### 6.6 Input

- One byte per player, written before every tick: bit 0 up, 1 down, 2 left, 3 right,
  4 action; the remaining bits reserved as 0 until the profile assigns them.
- Up to 8 local players. In Lua: `btn(b [, player])`, player from 1 to 8, default 1.
- Keyboard and controller arrive already merged into the same byte: the cartridge does not
  know (and must not know) which device a key comes from.

### 6.7 What the system does not do for the cartridge

- **Network and remote multiplayer**: no handling at system level (no host/join in the
  menu). If a game wants them, it builds them itself.
- **Free pixel drawing**: depends on the profile; a convenience API is only a wrapper
  around what the machine really has, not new hardware disguised as a function.
- **Saves**: not designed (§10).

## 7. Machine profile

The `.b16` container is independent of the machine. The project that adopts it must write
a **profile**, with at least:

- [ ] internal format of every bank type (`MAP `, `GFX `, `PAL `, `ICON`): bytes per
      cell, per tile, per color; byte order;
- [ ] size of the resident region of every type (at the maximum) and how `bank_size` is
      derived from the section parameters;
- [ ] maximums: world (reference 8×8 screens), number of tiles, palette;
- [ ] tick rate (reference 60) and per-tick budget;
- [ ] Lua dialect and exact sandbox list;
- [ ] machine API: names, signatures and semantics (including the swap functions);
- [ ] constants exposed to the cartridge;
- [ ] input layout beyond the 5 basic bits;
- [ ] **conformance vectors** (§9.5).

A rule for the profile: every value derived from others (sizes, positions) is
**recomputed from the formula** in every implementation, not copied as a number.

## 8. Life cycle

### 8.1 Working folder

Cartridges in progress are **folders**, finished cartridges are **files**:

```
cart/<name>.b16           finished cartridges: only to be played
dev/<name>/               cartridges in progress: the editor opens and edits them
    meta                  title, author, uid (generated when the folder is created)
    code.lua              CODE section
    map<N>.bin            bank N of the MAP section  (same format as the bank)
    gfx<N>.bin            bank N of the GFX section
    pal.bin               PAL section
    icon.bin              ICON section
```

- The `uid` is born **when the folder is born** and stays in the `meta` file: repacking
  does not change the identity of the cartridge.
- Every `.bin` file is already a bank in the final format (§2.11).
- Folder names are validated: no empty name, no `.` or `..`, no `/` (a name like
  `../../etc` typed in the editor would become a path outside `dev/`).

### 8.2 Testing without packing

The editor starts the game **directly from the folder**, with the same installation it
would use for a `.b16` file (same banks, same sandbox, same budget): the write → test →
fix loop does not go through the packer. During the test, Esc **closes** the game and goes
back to the editor (it does not suspend it: a suspended state during testing is
confusing).

### 8.3 Packing

`dev/<name>/` → `cart/<name>.b16`: header from `meta`, section table, banks appended in
order, CRC. The packer applies all the checks of §3.7 and the cap of §5.1 and **refuses**
instead of writing an invalid cartridge.

### 8.4 In the menu

- The menu shows **either** the finished cartridges (`cart/`) **or**, in development mode,
  those in progress (`dev/`, with a first "+" entry to create a new one): never both
  together. Development mode is remembered from one boot to the next.
- Title and author come from the header; the image from the `ICON` section if present.
- Shape of the icon: a large SD card with the **bottom-left corner cut off**. It is only a
  graphic idea for the menu, not a physical cartridge.
- Switch-style **suspend**: launching a game does not close the system; Esc from the game
  **suspends** it and goes back to the menu; coming back resumes exactly where it left off.
  Launching another cartridge while one is suspended asks for confirmation.

### 8.5 What the bm SDK already prepares (2026-10-04)

The format is not there yet; the console's SDK (`carts/editor/main.lua`) prepares the
ground without making anyone believe the engine uses it (§2.12):

- **project target**: on the project page **b** switches from `.bm` to `.b16`
  (remembered per file, in the SDK save). The file is always saved as `.bm`: the target
  only changes what the dev kit checks;
- **cap**: the dev kit (F1 again) shows the saved file against the **8 MiB** of §5.1, with
  a bar (green, yellow above 75%, red beyond);
- **contract**: with the `.b16` target the dev kit lists the lines of code that use what
  the sandbox of §6.3 will not have: `math.random` (§2.9), `time()`, saves (§10), `ls()`
  and files, the `cart_*` functions, the `udp_*` network, `require`, `load`, `screen()`
  (§2.6), and 3D, which waits for the machine profile (§7). It is a list of reminders, not
  a packer: when the format arrives, the real checks will be those of §3.7 and §8.3;
- **memory**: the dev kit estimates the memory of the data (sheet, map, models, sounds,
  z-buffer: the same sum as `stat(13)`) and, after a test (F5), the peak RAM, the fps, the
  ms and the instructions of the heaviest frame: the numbers on which to choose the
  profile's maximums (§7);
- **tokens**: the SDK and the overlay count them (`stat(11)`, `code_tokens()`), but as
  information: consistent with §2.4, no cap, neither in `.bm` nor in `.b16`.

When the format is developed, the working folder (§8.1) and the packer (§8.3) can start
from the SDK project: code, sheet (the `GFX ` banks), map (the `MAP ` banks), palette
(`PAL `) and cover (`ICON`) are already all there.

## 9. Mistakes not to repeat

Real problems met with this kind of format, and the rule that came out of them.

### 9.1 "Packed" structures and alignment

A header read as a *packed* C structure puts 32-bit fields at unaligned addresses: on x86
it works, on ARMv6 (Raspberry Pi 1 and Zero) the access can fail with SIGBUS, and the
problem only shows up on real hardware. Without *packed*, instead, the compiler adds
padding and the "256-byte" header becomes longer without anyone deciding it.

Rule: the offsets are fixed by **the specification** (§3.1), every field is aligned to its
size, and the reader reads the fields **byte by byte** in little endian, without overlaying
structures on the buffer.

### 9.2 Derived constants copied by hand

A size (the map) derived from other constants and determined the position of everything
that came after it in memory. It changed several times; a separate implementation had
copied it as a number and fell behind, reading the data at wrong offsets without any
visible error.

Rules: the machine's memory is fixed at the maximum (§2.5); what varies per cartridge
lives in the file; what derives from something else is recomputed from the formula (§7).

### 9.3 A budget that does not protect

Three holes found in the count hook, all verified with direct tests: it does not fire in
JIT-compiled code; it does not propagate to coroutines; it was not armed during the
top-level code and `_init()`, and a `while true do end` there blocked everything.
Remedies in §6.4. Every remedy must come with a **negative test** (the test that really
fails without the remedy).

### 9.4 Invisible crashes

A cartridge that crashes on the first tick and goes straight back to the menu looks like
it "doesn't start". The message goes on the screen (§6.5): the user often has no terminal.

### 9.5 Two implementations, a single behavior

If several implementations run the same cartridges, **conformance vectors** are needed:
test cartridges plus a text file with, for every tick, the input and the CRC-32 of memory
and image (or `crash` if that tick must crash). Generated deterministically (regenerating
them gives identical files); an implementation is conformant if it reproduces them all.
Every difference found is resolved in the specification and covered with a new vector.

### 9.6 Fields for modes never used

A field reserved for a future mode (a second screen format) stayed a placeholder for
months, constrained editor and maps, and was removed. Rule §2.6.

## 10. Open questions

- **Split of the cap** between code, maps and graphics: no imposed quota, only guidelines
  to write when there are real games.
- **Graphics banks of declarable size**: today `bank_size` is one per section and fixed by
  the profile; can a graphics bank smaller than the maximum be allowed, as for the world
  (§2.5)?
- **Audio banks** (`SFX `, `MUS `): reserved types, format to be designed together with
  the audio profile.
- **Saves**: not designed. Natural proposal: one file per cartridge, named after the
  `uid`, outside the cartridge (which is never written). Also to be decided what happens
  to the suspended state when the machine is switched off.
- **Reading banks from the SD on demand** instead of loading the whole file into RAM: with
  an 8 MiB cap, loading it whole is simple; if reading on demand were needed, a CRC per
  section (today `reserved` in the entry) would allow checking every bank when it is read.
- **SHA-256 and authenticity**: reserved field; external registry, signatures,
  distribution, possible NFTs: not designed, outside the engine.
- **Download and distribution** of cartridges: on hold.
- **Computation extensions** (§2.8): not designed.
- **The cap and the name**: 8 MiB comes from the SNES reference; if the "16" in the name
  should also become the cap (16 MiB), it is a decision to take now, before the first
  cartridge.

## 11. Glossary

- **Cartridge**: the `.b16` file, a whole game.
- **Section**: an entry of the table; a type of content (`CODE`, `MAP `, ...).
- **Bank**: a unit of a section, of fixed size, selectable by number.
- **Resident**: the bank currently copied into the machine's memory.
- **Swap / selection**: copy of a bank into the resident region, at the game's request.
- **Stage**: a map bank, that is, a world.
- **Maximum**: the largest value a cartridge can declare; memory is always sized on it.
- **Cap**: the byte limit of the whole file (8 MiB).
- **Machine profile**: the specification of the machine that runs the cartridges (§7).
- **Tick**: one game step (60 per second): input, `_update()`, image, audio.
- **Essential**: a section that a reader must understand to run the cartridge.
