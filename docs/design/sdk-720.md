# Design: SDK 720×720 Layout on RGB30 (R39)

> **Scope**: `carts/sdk_b16/` (`main.lua`, `layout.lua`, `build.py`) for PowKiddy RGB30.
> **Rule**: `carts/sdk` (Pi version, 640×360) is not touched. No changes to files outside `carts/sdk_b16/`.
> **Hardware verification**: The local environment has no physical RGB30 device; verification relies on static analysis, consistency scripts and the test suite.

---

## 1. Dimensions and Text Grid

| Parameter | Current (360×360) | R39 Target (720×720) | Notes |
|---|---|---|---|
| **Screen resolution** | 360 × 360 pixels | 720 × 720 pixels | Native resolution of the RGB30 ST7703 DSI panel. |
| **Text cell** | 8 × 16 pixels (`CW=8`, `CH=16`) | 8 × 16 pixels (`CW=8`, `CH=16`) | Kept identical to preserve clarity and density. |
| **Text columns** | 45 columns (`COLS = W // 8`) | **90 columns** | Doubles horizontal space; removes the `narrow` mode. |
| **Total text rows** | 22 full rows (22.5) | **45 full rows** | Vertical space more than doubled. |
| **Work region (`R.view`)** | 360 × 272 px (17 rows) | 720 × 664 px (**41.5 rows**) | Ample room for side-by-side panel/canvas. |
| **`LY.narrow(w)` state** | `true` ($360 < 480$) | **`false`** ($720 \ge 480$) | Natively enables the two-column side-by-side layout. |

---

## 2. How `layout.lua` Computes Areas

The [`layout.lua`](../../carts/sdk_b16/layout.lua) module divides regions via:
- `LY.split(r, dir, sizes)`: splits vertically (`"v"`) or horizontally (`"h"`). Sizes can be numeric pixels, rows (`"Nr"`), columns (`"Nc"`) or dynamic fractions (`"*"`).
- In [`main.lua`](../../carts/sdk_b16/main.lua), the master frame is defined at lines 70-71:
  - `R.tabs, R.body, R.hints, R.status = table.unpack(LY.split(LY.rect(0, 0, W, H), "v", { 16, "*", 16, 24 }))`
  - `R.strip, R.view = table.unpack(LY.split(R.body, "v", { "2r", "*" }))`
- At 720×720, with $W=720$ (90 columns), `R.view` can be split horizontally into two fixed columns:
  `local PANEL, WORK = table.unpack(LY.split(R.view, "h", { "30c", "*" }))`
  - **`PANEL`** (30 columns = 240 px): commands, tools, palette, layer list and properties.
  - **`WORK`** (60 columns = 480 px): native 3D viewport, high-resolution sprite/map canvas or code editor.

## 3. File Analysis

1. **`carts/sdk_b16/layout.lua`**:
   - Provides the geometric primitives (`rect`, `split`, `snap`, `fit`, `wrap`, `narrow`).
   - `L.narrow(w)` automatically recognizes that $720 \ge 480$, disabling forced stacking.
   - Needs ergonomic helpers for the two-column side-by-side layout (`L.side_by_side(r, panel_cols)`).
2. **`carts/sdk_b16/build/build.py`**:
   - Inserts `layout.lua` as a local closure before `main.lua` and computes the line offset for error messages.
   - Contains no hardcoded resolution constants; it stays unchanged and transparent with respect to 360 vs 720.
3. **`carts/sdk_b16/main.lua`**:
   - Contains the main framing and the submodules (`P.code`, `P.sprite`, `P.map`, `P.d3`, `P.menu`).
   - Needs to replace the fixed values inherited from 360 (e.g. canvas `192`, sheet `144`, `COLS=45`) with sizes relative to `PANEL` and `WORK`.

---

## 4. Identified Technical Risks

1. **3D/2D Fillrate and Performance**: 720×720 is 518,400 pixels ($4\times$ the 129,600 pixels). On RK3566 with software rendering or VOP2, fill and 3D rasterization routines must avoid unnecessary full redraws by using dirty rects.
2. **Physical Font Size**: An 8×16 text cell on a 4-inch 720×720 panel (≈254 DPI) produces small characters. Legibility of `prompt()` icons and status chips must be ensured with sharp contrast.
3. **Hardcoded Assumptions**: Absolute coordinates were found in some game templates and internal selectors that must adapt dynamically to `SCREEN_W` and `SCREEN_H`.

## 5. Breakdown of Next Steps (all $\le 45\text{ min}$)

- **Step 2 (layout.lua)**: Add helpers for the 2-column side-by-side partitioning (`PANEL` / `WORK`) and reactive handling of screens $\ge 480\text{ px}$.
- **Step 3 (Framing & P.code)**: Adapt the global `R.body` frame and support the code editor on 90 columns and 41 visible rows.
- **Step 4 (P.sprite & P.map)**: Side-by-side layout for the 2D pages: sprite sheet/palette in the side panel and expanded work canvas/grid.
- **Step 5 (P.d3 & Validation)**: Expanded 3D viewport with side controls/layer panel; full `consistency.py check` and regression tests.
