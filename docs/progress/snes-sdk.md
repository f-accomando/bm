# bm SNES SDK

Area sheet for the SNES SDK of bm: tools to make SNES games inside bm, in 65C816 assembly, with the keyboard and the mouse.
Back to [snes.md](snes.md) (the emulator that runs the ROMs). What is missing, in order: [snes-sdk-roadmap.md](snes-sdk-roadmap.md). Phase 1 of the plan is the assembler, the ROM builder, the code tab, the debug API, the sprite tab and the templates. This sheet covers the assembler and the ROM builder. Other sessions do the debug API and the sprite tab.

## The API

```lua
local A = require("snes_asm")
local res = A.assemble(source, { name = "main.s", read = function(path) return text or nil end })
if not res.ok then print(A.format_errors(res)) end        -- "main.s:12: message", one per line
local rom, info = A.build_rom(res, { title = "MY GAME" }) -- a string; give it to snes_load(rom)
local text = A.symbol_table(res)                          -- "$00:8000 reset", "= $10 counter"
local rom, res = A.build(source, opts, header)            -- both steps; on an error: nil, text, res
```

- `res.segments`: the code blocks `{ addr, data }`. `res.symbols`: name to value. `res.symlist`: the sorted list. `res.errors`: `{ file, line, msg }`.
- `read(path)` gives the text of `.include` and the bytes of `.incbin`. The default reads with `io.open` (the host tools only). A cart gives its own reader (for example `doc_read`).
- `A.opcodes` and `A.lengths` are the tables of the assembler (read only). A disassembler can use them.
- Header options (`build_rom`): `title`, `map` (`lorom` or `hirom`), `fast`, `sram_kb`, `battery`, `region`, `dev_id`, `version`, `chipset`, `fill`, `min_kb`, `vectors`.
- Vectors: `reset`, `nmi`, `irq`, `cop`, `brk`, `abort`. The builder reads the label of the same name (also in upper case). `vectors = { nmi = "my_nmi" }` or a number sets one. `emu_nmi`, `emu_irq`, `emu_cop`, `emu_abort` set the emulation vectors. `reset` is required. A missing vector points to an RTI that the builder writes at `$00:FFE0`.
- The ROM size is a power of two (32 KB minimum for LoROM, 64 KB for HiROM, 8 MB maximum). The builder writes the header at `$FFC0-$FFDF` of bank 0 and the vectors at `$FFE4-$FFFF`. It writes the complement and the checksum last.

## The language

- Case: mnemonics and directives ignore the case. Labels keep it. Comments start with `;`.
- Labels: `name:`. A local label is `@name:`; it belongs to the last global label. Many labels can stand on one line. An equate is `name = expression` (it can refer to a label defined later).
- Numbers: `$FF`, `0xFF`, `%1010`, `123`, `'A'`. `*` is the address of the instruction.
- Operators: `+ - * / %`, `<< >> & | ~` (`~` is xor between two values and NOT before one), `== != < > <= >=`, `&& ||`, `!`. Prefix operators: `<` low byte, `>` high byte, `^` bank byte. They take the whole expression after them: `#<table+1` is the low byte of `table+1`.
- Directives: `.org`, `.byte .word .long .dword` (also `.db .dw .dl .dd`), `.res n[,fill]` (`.ds`), `.align n[,fill]`, `.incbin "file"[,offset[,length]]`, `.include "file"`, `.a8 .a16 .i8 .i16`, `.lorom .hirom`, `.macro name p1, p2` ... `.endmacro`, `.rept n` ... `.endr`, `.if expr`, `.ifdef`, `.ifndef`, `.else`, `.endif`, `.error "text"`.
- Macros: the parameter names are replaced as whole words in the body. `\@` gives a number that is new for each call: `loop\@:`. A macro can call a macro (16 levels).
- Addresses are 24 bits. `.org $8000` is bank 0. `.org $018000` is bank 1. A `.res` leaves a gap that the builder fills with the padding byte.
- Width tracking: the assembler tracks M and X in the order of the source. `.a8 .a16 .i8 .i16` set them. `REP #const` and `SEP #const` set them too (the operand must be a constant). The state at the start is 8 bits for both. The width decides the size of `lda #`, `adc #`, `and #`, `bit #`, `cmp #`, `eor #`, `ora #`, `sbc #` (M) and of `ldx #`, `ldy #`, `cpx #`, `cpy #` (X). `rep`, `sep` and `pea` do not depend on the state. `xce`, `plp` and `rti` do not change the state in the assembler: use `.a16` after them.
- Operand size: a value known in pass 1 picks the smallest form (direct page, absolute, long). A symbol that is not defined yet is absolute. Force a size with `z:` (direct page), `a:` (absolute, keeps the low 16 bits), `f:` (long) before the operand, or with `.b .w .l` after the mnemonic (`lda.l label`). `jmp` and `jsr` to an address in the bank of the instruction use the absolute form; another bank uses the long form. `jml` and `jsl` are always long.
- Special: `brk`, `cop` and `wdm` are two bytes (`brk` gives signature 0; `brk #n` sets it). `mvn src,dst` and `mvp src,dst` are written source first. `pea` takes `$1234` or `#$1234`. Aliases: `bge` `blt` `ina` `dea` `tad` `tda` `tas` `tsa` `swa`.
- Errors: each has the file and the line. An error in a macro also names the macro and the line of the call. The assembler reports up to 200 errors.

## The app: bm SNES SDK (`bm/snes_sdk`)

- One SDK, many tabs: the SDK is ONE app with a tab bar (Code, Sprites, Map, Music, Run; F1 to F5; Ctrl+L opens the lesson window). A new tool of the SDK is a new tab in `bm/snes_sdk/main.lua`, not a new app. The Code and Run tabs work (the lessons are a window of the Code tab). Map and Music say "coming soon".
- Code tab: the editor of the `.s` and `.inc` files of the project, on `snes_asm`. The files are in `/docs` (8.3 names; `doc_read`, `doc_write`). The project keeps the names of the open files and the main file in the line `--code main=... files=...` of the data between the marks. A new project opens `main.s` (from `/docs`, or new with the reset snippet).
  - Keys: Ctrl+B build, F1 help on the instruction (a short help shows in the status line when the cursor is on one), Ctrl+G go to a label (the label under the cursor, or a list; a double click on a label name goes to it), Ctrl+F find, F6 and F7 next and previous match, F8 next error, Ctrl+J snippets (reset, nmi, dma, joypad, colour; each line has its comment), Ctrl+E the files (open, new, save all, main file, close), Ctrl+W close the file, Ctrl+S save the sources (and the project when it has a name), Ctrl+Q start or stop a selection, Ctrl+C/X/V/K/D copy, cut, paste, cut line, copy line down. The mouse puts the cursor, drags a selection, scrolls with the wheel and clicks an error or a file tab. F1 in another tab opens the Code tab.
  - Build: the buffers are saved, then `snes_asm` assembles the main file (`.include` reads the open buffer, else `/docs`) and the ROM builder writes `<project name>.sfc` (or the stem of the main file) to `/docs`. The size of the ROM is 32 KB minimum. The title in the header is the name in upper case (21 characters at most).
  - Errors: `SC.plain` turns the message of the assembler into plain words with what to do (A 8 bit and a 16 bit value: `rep #$20`; X and Y: `rep #$10`; an unknown word: the nearest instruction; a label that does not exist; a branch that is too far: `brl`). The first error shows under the cursor line, all errors are in a list (file, line; click to go there).
  - The F1 texts come from `A.opcodes` (the modes, the opcodes and the lengths are read from it) and from the datasheet facts of the cycles and flags. A test checks that every opcode of the table has a text.
- Run tab: F5 (or Ctrl+B) builds the project of the Code tab and runs the ROM in the SNES core, with the picture on the left and the panel on the right. F5 in the Code tab builds and runs again. F5 in another tab shows the Run tab (a build when nothing runs). F5 when the CPU is stopped continues. F9 sets or clears a breakpoint at the cursor line (Code tab) or at the PC (Run tab, stopped) or at an address typed in (Run tab, running). A breakpoint shows as a red square in the gutter of the Code tab, and the line where the CPU stopped has a `>`. F10 steps one instruction (the first F10 on a running game pauses it). Space pauses. The machine runs only while the Run tab shows. With no breakpoint armed the loop is `snes_frame`'s: the C hot loop has no debug check.
  - Panel: A X Y S D DB PB PC P with the flags (N V M X D I Z C: capital letter set, small letter clear; emulation mode shows `-` and `B` for bits 5 and 4) and the set flags in words, the source line at the PC, the breakpoints, then a hex view with four spaces: RAM (24-bit CPU space, `snes_peek`), VRAM, CGRAM and OAM (`snes_mem`). Keys when stopped: `g` go to an address, `w` write `address=bytes` (`snes_poke`, CPU addresses), `b` toggle a breakpoint at an address, `c` clear all, Tab next memory, arrows and PgUp/PgDn scroll, Ctrl+R reset. The mouse: click a memory name, `go` or `poke`, the wheel scrolls.
  - The map of lines and addresses is `res.lines` of `A.assemble` (instruction lines only, not macro lines). A breakpoint keeps its source line: a build finds the new address. F9 builds first when a text is not the same as at the last build. Lines that move because of an edit keep the old marker line until the next build.
  - Tests: `make test-snes-run` (the helpers, with the assembler map) and `make test-studio` (the whole tab in the host SDK test, with a stand-in machine; the C core is in `make test-snes-debug`). No Pi or RGB30 run.
- Lesson window (key Ctrl+L, in the Code tab; there is no Learn tab): 14 original lessons in English, one data file each in `bm/snes_sdk/lessons` (the order is in `LIST`). The Makefile puts them in the built `main.lua` as the table `SNESLESSONS`. Format and helpers: `core/lua/sneslearn.lua` (head `title:`, `goal:`, `link: Name | https://...`, then `---`, text, `## heading`, fenced blocks `asm` (a whole program) or `text`, `try:` lines). Each `asm` block has `expect=`, `frames=` and `pad=` for the test.
  - Lessons 1 to 5 are the theory (CPU, modes, addressing, memory, header). Lessons 6 to 14 are a course: ONE program grows (start without errors, clean start, colours, tiles, sprite, pad, move, flip and walk, jump). Each lesson has a `text` block (the part to add, with the mark where it goes: NAMES, SETUP, INPUT, LOGIC, DRAW, NMI, DATA) and an `asm` block (the whole program so far). The lessons are written by `core/scripts/snes_lessons.py`: edit the parts there and run it. Every program runs in the core with a check of its result.
  - Layout: Ctrl+L opens the window at the right half of the Code tab. The editor stays at the left and works as always (build, F5, errors, typing). With the window open, Ctrl+L gives the keys to the other side (editor or lessons); Esc or F1 in the lessons give them to the editor. Ctrl+Shift+L, or the `x` in the header of the window, closes it. A click on a side gives the keys to that side. The side that has the keys is the lit one (the header of the window, or the file tab). Tab is not a switch: the editor needs it. The header has `<` and `>` (other lesson) and the title (a click lists the lessons; the key `g` does the same).
  - Keys of the editor from the shell code editor (`B.nav` in `core/lua/asmbuf.lua`; the modifiers come from `keydown` through `M.mods` in `main.lua`, because `keyp` does not tell them): Shift with a move key selects (a move without Shift clears that selection; a Ctrl+Q mark stays), Ctrl+Left/Right a word, Ctrl+Alt+Left/Right the start/end of the line, Alt+Up/Down a page, Ctrl+Alt+Up/Down the start/end of the file. The lessons take Alt+Up/Down as a page and Ctrl+Alt+Up/Down as the start/end of the lesson.
  - Each code block: `i` Insert at the cursor of the current Code file (Ctrl+Z in the Code tab undoes it); `o` Open as new file (`lessNN.s`, then `lessNN_2.s`, ... in `/docs`; it is added to the open files; the file you are in stays the current one); `r` or Enter Run alone (builds the block as the scratch file `(lesson)`, loads it in the machine and shows the Run tab; no file and no ROM is written; the Run tab says "lesson example"; F5 or Ctrl+B runs your project again). Mouse: the buttons on the bar of each block. `n`/`p` select a block, `m` marks it (Notes), `l` lists the marks, `d` marks the lesson done, Left/Right the other lesson, Ctrl+F searches all the lessons.
  - Saved in the `.bme` Lua section between `-- snes-learn:begin` and `-- snes-learn:end` (outside the `snes-sdk:` marks): the last lesson, the read position and done mark of each lesson, the notes. The window is closed when a project opens. Nothing is written for a project that never used the lessons.
  - Tests: `make test-snes-learn` (every example assembles and runs in the core with the checks of its `expect=`; Insert, Open and Run alone keep the files byte for byte; marks survive a save and an open) and `make test-studio` (the whole window in the host SDK test: `tests/studio/snes_sdk_learn.lua`).
- Cartridge settings (Esc menu, "Cartridge..."): the map (LoROM or HiROM), the ROM speed (SlowROM or FastROM), the ROM size (32 KB to 4 MB, the builder makes it larger when the code needs it), the save RAM (none, 2, 8, 32, 128 KB) with a battery switch, and a coprocessor: none, DSP-1, Super FX, SA-1 (the core runs these three) and OBC-1, S-DD1, S-RTC, Cx4, SPC7110 (header only: the core has no chip yet; the status line says so). The settings are the chipset byte and the map byte of real cartridges (`SC.cart_header` in `core/lua/snescode.lua`). They are kept in the line `--cart` of the project and used by every build. The Super FX and the SA-1 force LoROM and save RAM; HiROM forces 64 KB. Test: `make test-snes-code`.
- Frame: the project is a `.bme` in `/bme` (Ctrl+N new, Ctrl+O open, Ctrl+S save, Esc menu). The sheet is its SHEET8. The data of the Sprites tab is text between `-- snes-sdk:begin` and `-- snes-sdk:end` in its Lua section: depth, sizes, the sub-palettes (BGR555 words) and the sub-palette of each tile. Other tabs keep their own data outside these marks.
- Sprites tab: depth 2/4/8 bpp, the size pairs 8/16, 8/32, 8/64, 16/32, 16/64, 32/64 (small or large), 8 sub-palettes of BGR555 with colour 0 clear, 5-bit channel bars with a live preview, the sub-palette of each tile on the grid, a sprite editor (pencil, fill, mouse or keys), an OAM preview (flip X, flip Y, priority, palette bits), PNG import with the quantiser (15 colours + clear), export of `.chr` (planar tiles, rows padded to 16 tiles: use a sheet 128 wide) and `.pal` (all sub-palettes, low byte first) to `/docs`.
  - Layout: the left column has the sprite editor at the top (about half of the height) and the OAM preview under it. The right column has the depth, the sizes, the sub-palette and the colour, and the sheet under them. The sheet zoom is the largest that shows the whole sheet, but not less than 1. When the sheet does not fit, the view shows a part of it and follows the sprite (`M.sox`, `M.soy`); the info line gives the part.
  - The pencil held: Space (or the pad's A) paints the pixel and starts a stroke. While the key stays held, each pixel the arrows (or the DPAD) go to is painted too. Del held clears in the same way. One stroke is one undo step. The mouse paints while its button is held.
- A ROM, read only, beside the project (Ctrl+O lists the `.sfc` and `.smc` of `/snes` and `/docs` after the projects; Esc menu "Open a ROM"; a `.sfc` from the file manager opens a new project and the ROM). Your project stays open at the left and keeps all its keys. The ROM is never written. The module is `core/lua/snesrom.lua` (the global `SNESROM`); the state is `RX` in `main.lua` (`RX.v` the ROM, `RX.side` the Sprites view, `LN.view` the view of the right window).
  - Code tab: the ROM is a view of the right window, the same window as the lessons. Ctrl+T swaps the two views (the row at the top of the window also has them). Ctrl+L gives the keys to the other side. The view is one read-only buffer: the disassembly of one bank from an address (the reset vector first). The head lines give the title, the map, the size, the chips, the save RAM, the region and the vectors. Each line is assembly text with the address and the bytes in its comment. The vectors and the targets of the jumps and branches have labels (`reset:`, `L808123:`). `rep` and `sep` change the widths and write `.a16`, `.i8` lines. Keys: `i` puts the line (or the selection) into your file at the cursor, Ctrl+C copies, `r` runs the ROM in the Run tab (F5 builds and runs your project again), F9 a breakpoint (the CPU stop puts the cursor on its line), Ctrl+E the vectors, an address, the bank before or after, the widths of A and X at the start, Ctrl+G a label, Ctrl+F, F6, F7 find. A double click on a label name goes to it. Other keys say "read only".
  - Sprites tab: Ctrl+T shows the ROM's tiles at the right instead of your panel and your sheet; your sprite and its preview stay at the left. The right column has a row of views at the top, as in the Code tab: Panel, ROM, OAM (a view that is not there yet is dim; a click on it says how to get it; a click on a view opens it; Ctrl+T goes to the next one). A page is 128x128 in greys, drawn once into a render target and shown at the largest zoom the column allows (2 on 640x360). Alt+Up and Alt+Down a page (PgUp and PgDn too), Ctrl+Alt+Up and Ctrl+Alt+Down the start and the end of the ROM, as in the Code tab; `<` and `>` one tile, `j` an offset or a CPU address, Shift+B the depth of the ROM's tiles (2, 4, 8 bpp; the project's depth does not change). A click moves the box (the size of your sprite); `c` or a double click copies it; Ctrl+V puts the indices in your sprite.
  - OAM view (Sprites tab): Ctrl+T goes from your panel to the ROM's tiles (a ROM open), then to the OAM view (the machine of the Run tab has a ROM: `r` in the ROM view, or F5 for your project), then back to your panel. The view reads the machine once after each run: the OAM (`snes_mem("oam")`), the video RAM, the colour RAM and OBSEL (from `snes_debug().regs`). It shows the picture at half size with a box on each sprite that shows, the numbers of the sprite chosen (place, tile and name table, size, palette, priority, flips), the sprite in its colours, and the list of the sprites that show. Keys: `<` and `>` the sprite that shows before or after, `n` and Shift+N all 128, `c` (or a double click) copies its pixels (4 bpp indices, not flipped; Ctrl+V puts them in your sprite), Shift+P puts its 16 colours in your sub-palette (4 bpp projects). A click on a box or a list line chooses the sprite. The module is `core/lua/snesoam.lua` (the global `SNESOAM`, no bm API; the rules of `draw_obj` in `core/src/bm/snes_ppu.c`). Test: `make test-snes-oam`, and the OAM steps of `tests/studio/snes_sdk_rom.lua`.
  - Test: `tests/studio/snes_sdk_rom.lua` (in `make test-studio`), with a ROM in a stand-in `/snes` folder. Checked by hand once with a real 512 KB LoROM: the header is right, a bank of 18792 lines takes 0.04 s on the PC.
- The pixels are indices in the sub-palette of their tile (the data); the colours of the runtime sheet come from the palette. A change of a colour repaints the sheet.
- Converters: `core/lua/snesgfx.lua` (no UI, no bm API). Test: `make test-snes-gfx`. Host test of the app: `tests/studio/snes_sdk_host.lua` (in `make test-studio`).
- Build: the Makefile adds the converter after `main.lua` as the global `SNESGFX` (`build/snes_sdk/main.lua`; a cart has no other Lua file). The cart reads it lazily (`G`), because the global exists only after the main chunk ran.
- bm Pixel keeps its own F7 page (the first version of the same tool, kept as it is). The SDK is the place for new SNES work: do not extend bm Pixel for it.

## Rules (do not break)

- The assembler is original code. The references (PVSnesLib, the ersanio course, the SMW disassembly, libSFX, the WDC datasheet) are read only: no code and no data from them enters the repository.
- The ROM goes to a buffer that the cart gives to `snes_load`. A cart writes a ROM file to `/docs` (`doc_write`). `/snes` is read only for carts: bm SNES reads `.sfc` and `.smc` from `/snes` and, for a ROM of the SDK, from `/docs`.
- The SDK opens a ROM read only, beside the project. Never write a byte of it: `i` and `c` copy from it into the project.
- One module `snes_asm` holds the assembler and the builder. Register a new built-in library in the same places as `snes_asm` (`core/src/bm/require.c`, `core/src/script/embed.S`, `core/src/rgb30/bm_embed.S`, `tests/host/libs.S`, `core/rgb30.mk`, `Makefile`, `core/scripts/mkweblibs.py`).
- The opcode test of `asm_test.lua` lists the 256 opcodes in the order of the opcode map, apart from the table of the assembler. Keep it so: the two lists check each other.
- Pass 1 decides the size of each instruction and pass 2 only writes bytes. A change to the size rules must keep the two passes equal.
- The Code tab has no Lua macros, no `.lua` blocks and no Lisp syntax (the user decided to leave them out). Do not add them to `snes_asm`.
- Each snippet of `snescode.lua` assembles by itself (with a `reset` label) and has a comment on every line. Add a snippet to the list and the test checks it.
- A new instruction or mode in `snes_asm` needs its F1 text in `snescode.lua` (the test fails without it).
- One SDK, many tabs: new SNES tools are tabs of `bm/snes_sdk`. Shared code goes in a module (`core/lua/`), never in the interface of another app.
- Keep the converters free of any bm API, so the PC tests run them.
- The Run tab runs the machine only while it shows and never adds a check to the C hot loop; the debug panel reads through `snes_peek`, `snes_mem`, `snes_regs`, `snes_step`, `snes_break` and `snes_run`.
- Register a new shared module of the SDK (`snesrun.lua`) in the build of `$(BUILD)/snes_sdk/main.lua` as a global (`SNESRUN`), as for `SNESCODE`.
- Write the text of docs and comments in ASD-STE100.
- A lesson example is a whole program that assembles and runs by itself, with an `expect=` check. A new lesson goes in `bm/snes_sdk/lessons/` and in `LIST`. Lessons are English and original: links to outside sources only, no copied text or code.
- The lesson window code is one function inside `main.lua` (the main chunk is at the limit of 200 local variables). Do not add top-level locals to `main.lua`: use fields of `LN`, `M` and `RX` (the ROM opened read only).
- The lessons 6 to 14 repeat the whole program so far. Change them only in `core/scripts/snes_lessons.py`, then run it and `make test-snes-learn`.
- The window draws the Code tab in the left half by changing `W` for the call of `draw_code`. Keep that call as it is: a new Code tab part that reads `W` works in both sizes.

10. NES emulator for the SNES core (user choice, 2026-11-16; ROADMAP APP-35). An SDK project that builds a `.sfc` which reads a `.nes` and runs it. Not started. Steps:
   1. The CPU: run the 6502 on the 65C816 (emulation mode e=1 or native mode). Intercept each access to `$2000-$2007`, `$4000-$4017` and the mapper writes. The decimal flag has no effect on the NES.
   2. The picture: write the PPU registers as SNES PPU, VRAM, CGRAM and OAM writes by DMA. Convert the 2bpp planar NES tiles to SNES 2bpp. Convert the 64 NES colours to BGR555. Map the attributes to BG sub-palettes. Use the sprite 0 hit through the H/V IRQ, and the split scroll through HDMA.
   3. The sound: an SPC700 driver for the pulse, triangle and noise channels. The DMC comes last.
   4. The input: `$4016/$4017` from the auto-read at `$4218`.
   5. The cartridge: map the ROM into LoROM banks. Start with mappers 0, 2 and 3, then 1 and 4. Use `core/src/bm/nes.c` as the reference to compare.
   6. Tests: a test ROM that `make_testrom.py` builds; run it in the core and compare the frame with `nes.c` (`tests/nes/`). Run nestest through the SNES program.
   Rule: bm NES in C (`nes.c`) stays the main emulator. The SNES program is an SDK showcase.
