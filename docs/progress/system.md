# System

Boot, memory, interrupts, fibers, crash handling, drivers (USB, SD/FAT, Bluetooth, WiFi),
the network stack and the kernel's menu and services on the Pi. RGB30 specifics:
[platforms](platforms.md). Hardware: [`docs/HARDWARE.md`](../HARDWARE.md).

## How it is today

### Boot (`core/src/boot/start.S`, `core/src/kernel/main.c`, `core/linker.ld`)
- Firmware loads `kernel.img` at 0x8000. `start.S`: core 0 only (others parked), HYP → SVC
  on the A53, stacks, `.bss` cleared (`.noinit` is not), the `bmK6`/`bmK7` tag at +4.
- `main.c`: UART, vectors, board (`core/src/drivers/board.c`), ARM clock to max, memory split
  from the firmware (`arm_memory_end`, `sdram_end`), MMU and caches, VFP, timer, IRQs,
  watchdog (3 s), crash report of the boot before, Bluetooth if paired, `wifi_boot()`,
  `eth_boot()`, then `carts_menu()`; the monitor after it.
- `make` also builds `build/chainloader.img` (`core/chainloader/`).

### Memory (`core/src/arch/mmu.c`, `cache.c`)
1 MB sections: the ARM's RAM cached (WB/WA), the GPU's share mapped uncached (normal), the
peripherals as device, the rest unmapped. `mmu_set_cached` switches ranges (GPU job memory,
`gpu3d_wc`). Heap through newlib `_sbrk` (`core/src/lib/syscalls.c`).

### Interrupts, time, fibers
- `core/src/kernel/irq.c` (BCM2835 controller, 64 sources), `tick.c` (system timer channel 1),
  `core/src/drivers/timer.c` (1 MHz counter).
- Fibers, shares, the `menu idle:` log: [multitasking](multitasking.md).

### Crashes and freezes (`exceptions.c`, `crumbs.c`, `core/src/drivers/watchdog.c`)
Exceptions show a red screen with registers and the call trail. Breadcrumbs and the last 4 KB
printed live in `.noinit`, survive a reset and become a report at the next boot
(`reports_text`), sent once the network is up. Watchdog: armed at 3 s (the Pi Zero W boot log says `watchdog: on, 3000 ms`).
`exception_handler()` sets the crash flag before all other work, so a restart from a hang in the handler is reported as a crash. The timer IRQ pets the watchdog through `watchdog_pet_irq()`, which pets only while the main code makes progress (`watchdog_progress()`, called by `crumb`, `crumb_frame`, `fb_flip` and the input polls). More than 20 s without progress: no pet, and the SoC resets 3 s later. `mbox_call` gives up after 2 s. Analysis of the freezes of 22-23 Oct: [watchdog-hang](../design/watchdog-hang.md).
Freeze of 26 Oct 2026 (Pi, 3 hours after boot, from the report `kind: freeze`): the VideoCore firmware stopped answering. Every `fb_init_depth` failed with `mbox_call failed`, the menu could not draw, the network stayed alive. Fixes (host and QEMU tested, not yet on the Pi): after `MBOX_DEAD_TIMEOUTS` (3) mailbox timeouts in a row `firmware_dead()` (`core/src/kernel/main.c`) sets a crumb and restarts through the watchdog; the next boot sends a freeze report. The kernel log (`klog`, 64 KB) keeps its first 12 KB and the last lines, with a marker (`bootlog_trim`, `make test-klog`); before, it stopped when full. A planned restart (`crumbs_restart`) saves the log to the SD first and marks the run as ended last. The nearby-console listening (`market_lan`) retries every 5 s, says it once with the lwIP error number, and the listener may reuse a port in TIME_WAIT (`SO_REUSE`, `SOF_REUSEADDR`): before, after a game received a moment ago it failed every frame and the next transfer found no listener. Open: the cause of the firmware stop is not known (the 3D, the QPU or the Market download are suspects); watch the next freeze report. **Second report, 30 Oct 2026** (Pi Zero W, kernel `v0.2.5-1980-g05596f65`, 2356 s after boot, report `nodate-3e205c_freeze_pi-zero-w_v0.2.5-1980-g05596f65.txt`): the menu was idle on the GPU (a native layout, 6 ms a frame); the Market had just saved its catalog (a TLS handshake of 224 ms, the fiber of the Market 60 ms past its slice). The user started the app `agent.bm`: the first `fb_init_depth` failed (`mbox_call failed`), `bm_video_enter` failed with -1, and `firmware_dead()` restarted the Pi. The app did not run: the video mode change failed before its code started. The two earlier Ctrl+Shift+Esc blocks of the user (the menu stops, or the monitor starts and the screen is not drawn) look like the same fault: a mode change after leaving a menu drawn by the GPU. Not verified. Done on 30 Oct 2026: the first timeout of a run prints `mbox: no answer on channel N to tag 0x..., (which wait), status ..., the last answer was N ms ago`, and the V3D error registers (`mbox_set_diag_hook`, `core/src/drivers/mbox.c`, `main.c`); not seen on the Pi yet. Next: run a day with `menu_scale=1` (the ARM draws the menu) and see if the stop does not come back.
**Search of 17-18 Nov 2026 (class B, Pi Zero W and Pi 1 through the bridge).** The fault: the first video mode change after the GPU menu (an app, the monitor, a kernel install restart) gets no answer to tag 0x48003. The kernel stays alive, the screen freezes, and the next app start ends in a watchdog restart. The details and the numbers are in [v3d](v3d.md) item 0. What was done:
- Crash record fix (19258768): the record now leaves the VideoCore L2 after its rare writes (`l2_push`). Before, a watchdog restart lost it: old records, false freezes, and the menu in safe mode on the ARM after clean restarts. This explained the report "after the watchdog restart, the freeze does not come back".
- Build (7b5c306c): no compiler warnings in the Pi, clean and RGB30 kernels.
- Suspects ruled out: the time in the menu (10 s and 600 s give the same rate), `gpu_mem=128`, the page on screen before the change, the V3D soft reset, the QPUs off during the change, V3D screen writes around the VideoCore L2, and the V3D ERRSTAT bits (a clean ERRSTAT at the change gave 6 of 60). The Pi 1 (composite) gave 0 of 6.
- Cause found: the risk grows with the number of V3D jobs in the menu. About 7000 jobs gave 6 of 60, about 1900 jobs 7 of 225, about 300 jobs 0 of 120, and the ARM menu 0 of 60.
- Fix (e61a4189): a still GPU menu draws 1 frame in 4. A move, a panel, a question, a notice or the pointer gives all the frames for 1 s. The vertex shader probe tries Mesa's way first, so it leaves no VPM error bits.
- Moving menu (f6495e27): 30 s of moves before the close gave 0 of 20. The bridge has the key `menu-move`, and `bm_net.py --keys` takes up to 64 keys.
- Test scripts: `out/hvs_rounds.sh` (restart, N s in the menu, `line log`) and `out/hvs_move.sh` (the same with moves). The test code of the search is in `out/v3d-menu-hvs-tests.patch`. These files are not committed.
- Open: the cause in the firmware is not known. Watch the Pi Zero W in daily use. If a freeze report with tag 0x48003 comes back, draw only the frames that change.

### USB (`core/src/usb/`)
Own DWC2 host stack (`dwc2.c`, `usb.c`). HID (`hid.c`): boot keyboards (IT/US layout),
generic HID gamepads (descriptor parsed), Xbox 360 wired, mice. `smsc95xx.c`: the Pi 1
B/B+ Ethernet.

### Storage (`core/src/drivers/sd.c`, `core/src/fs/fat.c`)
- SDHOST by default (`sdhost.c`), Arasan EMMC (`sd_emmc.c`, the Zero W's WiFi controller)
  if SDHOST fails a transfer twice; not on a failed multi-block write. `sd_counters()`
  (retries, waits run out) and `fat_cluster_bytes()` in the boot `sd:` line.
- FAT16/FAT32: long names read, whole files and 8.3 directories written. `store()`: the
  clusters marked as a chain first (`alloc_chain`), the data in runs of up to 32 KB read
  back (`fat_write_runs`, on; off for good on a mismatch), the last cluster only where it
  has data, then with no tick the entry found again (`locate`) and changed in one sector;
  the old chain released last. FAT entries change a sector per copy at a time
  (`fat_set_list`); the free-space search starts at FSInfo's hint.
- `fat_write_tick` (a write in a fiber yields): [multitasking](multitasking.md). `fat_writing()`.

## Rules (do not break)
- The Assistant's data (SYS-20, 28 Oct 2026): the dictionaries (`words.lua`) and the knowledge file (`assist.bin`) are not in the clean (shipped) kernel. They are blobs of the DATA section (type 15) of `assistant.bm` (`mkbm.py --data NAME=FILE`, `make build/assistant.bm`). `core/src/kernel/appdata.c` (`appdata_get`) reads them from `/bm/assistant.bm` at first use and keeps the file in memory. Without the app, `require "words"` and `ai.*` raise "the Assistant app is not installed" and the monitor key `I` prints "assistant: not installed". No kernel embeds them (`CLEAN_KERNEL` is gone since 16 Nov 2026). Do not embed them. The clean Pi kernel is 2.4 MB (3.75 MB before). Test: `tests/qemu_test.py -k assistant_app` (builds `build-clean/` on the first run). The RGB30 kernel has no `words`; it is unchanged. No kernel embeds an app (16 Nov 2026): bm SDK, Sound, Studio, Animator, Mesh, Pixel, bm Code and the Assistant come from Market > Apps. `embed.S` has no `*_cart` symbol. The Dev tab has the Monitor and Lua tiles, then the apps found on the SD card. Do not add a built-in copy of an app: it shows twice in Dev when the app is installed too. The system draws no splash at the start of a cartridge: do not call `loading_begin` (see [system-menu](system-menu.md)).
- The apps are files of `/bm` (18 Nov 2026). `ls("/bm")` gives `tool` (the tool id) for each app file of `kernel/toolnames.h`. Leave these files out of each picker of cartridges: `U.project_files` (bmui) and the list of bm Sound do it. A QEMU test that opens a tool puts its app on the card: `tools(b, ...)` with `mksd.build`, or `tool_drive(b, ...)` for a test with no card. Both add the Assistant (its dictionaries are the word completion). `make test-qemu` builds these apps (`QEMU_DEPS`).
- The bridge gate (26 Oct): `bm/bridge.txt` holds one word: `off` (default), `on` or `fast`. `off` refuses every operation of the transfer port (S, P, K, C, T, G; answer `BO`). `on` accepts them and stages a kernel. `fast` writes a kernel and a file at once (`dev_mode()`, the old `dev=1`). Only the user sets it: Settings > System > Bridge, or the file put on the SD card from a PC. `config_merge` refuses the keys `dev` and `bridge` (`BF`), and the transfer refuses any file named `bridge.txt` in any folder (`BF`). Do not add a network way to write this file.
- Build the Pi kernel, the clean Pi kernel and the RGB30 kernel with no compiler warning (17 Nov 2026: 0 warnings). Fix a new warning in its source. Use a local `#pragma GCC diagnostic` only for a table that leaves fields at 0 on purpose (`b3d.c` `tests[]`). Harm: the full install prints about 60 warnings, and a real one is lost among them.
- The bottom bar of the menu shows the key chips only. Put a failure of a user action in the notice box (`notice_fail()`) and any other message in the console log. Add no text line to the bar.
- A menu card shows only the cover. The cover of a game or an app comes from `core/scripts/mkartcovers.py` (88x88, one art style); the bm editors keep the covers of `core/scripts/mkcovers.py`.
- Settings shows a graphics choice only if a player can judge it by sight. Put every performance flag in `config.txt` as a hidden key, with no Settings row (SYS-9; table: [v3d-flags](v3d-flags.md)).
- All SD logs only via `core/src/kernel/sdlog.c`.
- The Monitor (`core/src/kernel/monitor.c`) is a table of commands. Add a command with ONE row in `commands`: word, arguments, one help line, handler (a group has subcommand rows). The help and the Tab completion come from that row. The bm shell has no hotkeys. Give a new function a command word, and a menu item in `core/src/kernel/shell_menu.c` if the user needs it often. A menu item is a line of commands. `:` takes one line from the menu and from the PC tools. Write no help text by hand. - Pet the watchdog only through `watchdog_pet_irq()` in the timer hook. Call `watchdog_progress()` in every new loop that the main code can sit in for more than 1 s and that does not call `crumb`, `fb_flip`, an input poll, `fiber_slice`, `net_wait_step` or an SD tick. Harm of a plain `watchdog_pet()` in the IRQ: a hung main loop is never reset (the Pi stayed frozen for hours on 23 Oct).
