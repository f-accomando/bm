# Tools and SDK

The on-console suite (bm SDK and editors), the assistant, the PC scripts, the Market, the
tutorial videos and CI. User guide: [`sdk/README.md`](../../sdk/README.md); resources:
[`docs/RISORSE.md`](../RISORSE.md).

## How it is today

### The suite (`carts/`, opened from the Dev tab or installed from the Market Apps page)
Detail of each editor (SDK, SDK for the RGB30, Code, Pixel, Studio, Animator, Mesh, Sound, Write), the Lib tab, shared Lua and projects (M47): [tools-suite](tools-suite.md).

### Assistant (`src/ai/`)
Details: [tools-assistant](tools-assistant.md). Tutorial videos (`video/`, series *Skyvale World*): [video](video.md).

### Market (`market/`, repo `f-accomando/bm-market`)
Games (`MARKET_GAMES`: `GAMES` without `MARKET_NOT`, so without `village`) and the bm editors
(`MARKET_APPS`: `editor`, `code`, `pixel`, `studio`, `animator`, `mesh`, `sound`, each with an explicit
`kind: app` line) reach the consoles from `bm-market`. The Pi gets each editor as `.bm` (built as
`build/<id>.bm`); the RGB30 gets the SDK as `.b16` under the same id `editor` (from `carts/sdk_b16`).
`assistant`, `write` and `typing` keep their place in the apps list of `is_known_app`.
`bm-market` has two folders with one layout: `games/<id>/` and `apps/<id>/`. `mkmarket.py games --apps apps`
reads both. An item of `apps/` is always `kind app`; an id exists in one folder only; the catalog keeps
one format (a `kind app` line), so old consoles work. `make market-seed MARKET=<clone>` puts the games
in `games/` and the apps (the editors, `typing`, `write`) in `apps/`. Then commit and push there
(`scripts/market.sh` from WSL). Removing an item from the seed does not remove it from the clone: run
`git rm -r games/<id>` there. The Market UI separates **Games** and **Apps** pages (`Y` / `V` or
subtab click) and shows `.bm` / `.b16` format badges on covers, title row and details panel.

### Tests on a real Pi (`tools/pi_bridge.py`, `tools/pi.py`, `tools/pi_test.py`)
The owner types the console password once in `pi_bridge.py`; a client (Claude Code, `pi_test.py`) then sends `line`, `send`, `play`, `kernel` through a local socket without seeing the password. It can run `gpu`/`b3d`, send a cartridge or a kernel and restore the normal one. `./easy_install.sh bridge [profile]` (menu 9) starts it for a saved profile with its board (`--board pi|zero2|rgb30`: `kernel FILE` takes only that board's kernel file; the RGB30 has no monitor, so its crash/freeze/reboot keys answer "not for this board"; test `tests/net/check_pi_bridge_board.py`, not tried on the RGB30). It sees the error of a stopped cartridge (`err`, R-NET1) and the screen (`shot OUT.png`, R-NET2: transfer ops `T`/`G`): [`design/pi-test.md`](../design/pi-test.md).

### CI (`.github/workflows/ci.yml`)
Build; host tests (`make test-host`); QEMU in four shards (`make test-qemu SHARD=K/4`); RGB30 build and QEMU
tests; signed release on a `v*` tag of a green commit. A new test over 20 s goes in `SLOW`. Three QEMU tests were steadied against flaky timing: `test_studio_animator` (short gap, the toast is brief), `test_usb_mouse` (wait for one icon), `test_code_completion` (wait for the colour). `test_code_completion`, `test_sd_cartridges` and `test_monitor_line` failed at times on CI and did not fail in 81 local runs (idle and under CPU load). The code read showed keys sent before the screen had changed. The tests now wait for the menu (`wait_menu`), for the cover after each key, and for "Tab:" to leave the status line. On a miss `test_code_completion` prints the screen text and colour counts and saves `build/diag/code-complete-miss.png`; `wait_menu` saves `build/diag/menu-not-drawn.png` and `.txt`; CI uploads `build/diag/`. Read these files when a test fails again. `test_code_editor` (failed once on CI: the two-page screen after F4) and `test_usb_mouse` (failed once on CI) were steadied the same way. Under CPU load `test_code_editor` failed in 7 of 12 local runs, always at "bm: copied": the answer key was sent before the question box was drawn, and the question's first poll ignores a key held at the start. The test now waits for the box (`copy_asked`). It also waits for the file list before Down and Enter and for each new tab before the next key, and `see` waits 20 s. `test_usb_mouse` failed in 1 of 12 runs, idle or loaded: the Left key moved two covers, because a slow menu frame lets the 500 ms key repeat (`hid.c`) fire. The test keeps a strict check (user decision, 22 Oct): the Left key is sent as press and release in one call, and it moves exactly one cover. It waits 15 s for each screen. On a miss `test_code_editor` saves `build/diag/code-editor-miss.png` and `.txt`. The artifact upload may fail without failing the job. RGB30 `test_update_from_sd` timed out under load (22 Oct): it sent its menu keys blind (`keys` with a fixed pause) and slept for the panels. The RGB30 menu reads a serial key as held for 120 ms (`PAD_SERIAL_MS`, `pad.c`), so a frame longer than that drops the press. Under 8 busy loops the old test failed 2 of 2 runs at "can be installed"; the new one passed 3 of 3 (64 s each). The test now sends each key with `press` (wait for the words the key brings to the screen, resend after 6 s) or `press_serial` (wait for a serial line), and has no fixed sleeps. The update code (`update.c`) has no short timeout: it is not changed.

## Rules (do not break)
- bm Mesh main chunk: 200 locals is the limit and the chunk is at it. Put new state and functions in the fields of `ed`, `lp` or `UA` (the undo helpers), not in new `local`s.
- bm Mesh hide: a hidden vertex is a number in `it.hid`. Any code that deletes or renumbers vertices must call `compact(it)` (it renumbers `it.hid` with `T.G.compact(it, sv, extra)`) and push the undo step with `begin_edit` or `UA.push`; the snapshot stores the set.
- bm Mesh bevel (`T.G.bevel_plan`, `T.G.bevel_apply`): plan first, change after. The first copy of a split vertex keeps its number; do not add a `compact` after a bevel. A vertex whose faces do not close in one fan is refused; do not bevel it by guessing. New state of the bevel and the projection lives in `ed` fields (`ed.bevel_text`, `ed.project_text`), not in new locals.
- bm Studio block shapes (`T.block_shape`): the faces look out because the function turns each face away from the mean of the corners. A new kind needs a convex shape and a line in the host test of closed meshes in `mesh_host.lua`. Ramp and corner rise away from the camera (`T.view_axes`).
- bm Mesh reference pictures live on the project's sheet below its rows (`proj.refs`). Export with `T.sheet_section(proj.refs.h0)`; never write those rows to a file.
- The ghost wire (`ed.ghost_draw` in `carts/mesh/main.lua`) draws at most `T.G.GHOST_EDGES_FRAME` edges in one frame. Keep the cap when you change the draw. The ghost detail (`ed.ghost_detail_i`) stays in the editor state and never goes into the model, the save or the undo.
- bm Animator, rig page: key `j` (pad menu: Head alone) makes a head chosen with Tab move alone (`rg.alone`; `rig_move` in `carts/animator/main.lua`). The bone keeps its parent, its tail and its poses; the move is refused when the bone would be shorter than 1/16; each move is one undo step; the tail and the joints behave as before. Host tests in `tools3d_host.lua` and `humanoid_host.lua` (shoulder and hip, no stub bone). Key and pad feel are not verified on the device.
- The humanoid test (`tests/studio/humanoid_host.lua`) types keys into bm Mesh and bm Animator and reads the status line and the rig line ("head of NAME: x, y, z"). When you change a key, a message or those lines in the two editors, change the test with them.
- The three editors import and export models with the flows in `src/script/bm3d.lua` (`T.import_flow`, `T.import_entry`, `T.export_item`); each editor passes its own `ui = {choose, ask, say}` and its own function that takes the item. Do not copy the file code into a cart. bm Mesh keeps its new functions in fields (`lp.import_dialog`, `lp.export_dialog`): the cart is at the limit of 200 locals.
- `res_write` writes only `/bmm/NAME.bmm` (NAME: 1 to 8 of a-z 0-9 _ -), only in a tool, and never over a file unless `replace`. The editors call `T.write_bmm`. Do not write `/glb`. `glb3d` never writes. It refuses a file over 16 MiB (`GLB3D_MAX_FILE` in `runtime.c`) and a model over 65535 vertices or triangles. Do not add another cap. The picture flow (`picture3d`) keeps its 4096 vertices and 16384 triangles (`format_limit` = 0).
- A new `.bme` is written in `/bme`, built with `bm_project_path()` (C) or `U.project_path()` (Lua). A `.bme` next to its game is read and saved where it is; the tool says so. Do not move a user file.
