## PUNTO APERTO P1 (da sciogliere da SPV prima della prima corsa SUL PI; non blocca il codice e i test dell'8a)
Il passo 4 ("`keys monitor` finisce il gioco") non funziona così com'è sul Pi reale, a quanto risulta dal codice: `bm_net.py --keys` rifiuta (exit 2: "the keys go to the application ...: back to the menu first (Ctrl-Esc on the console)") quando la console dice che i tasti vanno a un'applicazione (`tools/bm_net.py:341-352` `keys_blocked`, righe 457-468; il kernel annuncia `FOCUS_APP = "the application (Ctrl-\ back to the menu)"`, `src/kernel/carts.c:1137` e `:1945` `netcon_focus(...)`). Un gioco lanciato con `play FILE` (op `P`, `netxfer.c:565-571`: "the monitor or the menu plays it") passa dallo stesso menu e quindi, probabilmente, dallo stesso `netcon_focus(FOCUS_APP)`: `non verificato` (non ho letto il punto dove il menu consuma `play_buf`). Inoltre il bridge restituisce solo il testo (non il codice di uscita), e `--keys` accetta solo lettere e cifre (`bm_net.py:457`), non Ctrl-\ (0x1c). Conseguenza: o `keys monitor` funziona sul Pi (il gioco prende la `q`: `non verificato`) o il passo 4 risponde "back to the menu first" e il soak non può finire il gioco.
Come ci si comporta in questo WO: lo script esegue il passo 4 come specificato e, se la risposta contiene `back to the menu first` o `refused`, stampa il motivo ed esce 1 (caso di test 9: non si impianta e non si inventa un altro modo). Opzioni per SPV (decisione sua): (A) un WO a monte "R-NET8p": `bm_net.py --keys` e il bridge imparano un tasto nominato `menu` = Ctrl-\ (0x1c) che `keys_blocked` lascia passare (file di R-NET5/6: perimetro da aprire); (B) la prima corsa reale con `--minutes 1` e senza `--reboot` per vedere cosa risponde il Pi (ok dell'utente in chat); (C) accettare che il soak finisca solo con un reboot a gioco acceso (perderebbe i fps e "ended cleanly"): sconsigliata.

Passo 1: `tools/pi_soak.py` (nuovo, solo stdlib, `#!/usr/bin/env python3`, docstring di 6-8 righe con la sequenza, gli exit code e "WSL: needs Unix sockets"). CLI (`argparse`): `--cart FILE` (obbligatorio), `--minutes M` (obbligatorio, `float > 0`), `--every S` (default 60, `float > 0`), `--reboot` (flag), `--min-fps` (default 55, float), `--sock` (default `~/.pi_bridge.sock`, `os.path.expanduser`). Costanti di modulo: `POLL_REBOOT = 10`, `WAIT_REBOOT = 180`, `ASK_TIMEOUT = 320`, `FPS_LINE = re.compile(r'bm: "([^"]*)" (\d+) frames, (\d+\.\d) fps, (\d+) dropped')`.
 - `ask(sock_path, request)` → `str`: come `tools/pi.py:10-23` (un `AF_UNIX`, `settimeout(ASK_TIMEOUT)`, `sendall(request + "\n")`, lettura fino a `b""`, `decode("utf-8", "replace")`); se `connect` fallisce: `sys.exit("the bridge is not running (python3 tools/pi_bridge.py <ip>)")` (exit 1 di `sys.exit(str)` → usa invece `print(...)` e `return 2`: vedi gli exit code). Senza `socket.AF_UNIX`: stampa "needs Unix sockets: run it in WSL" e return 2.
 - `main(argv=None, sleep=time.sleep, now=time.monotonic)` → exit code (gli ultimi due parametri servono al test per un orologio finto; `if __name__ == "__main__": sys.exit(main())`). Sequenza:
   1. `s = ask("status")`: se non inizia con `status: up` → stampa le sue righe e `return 3` (nessun `play` è partito).
   2. `p = ask("play " + os.path.abspath(cart))`: se `p` inizia con `refused` o contiene `refused:`, `timeout:` o `no answer` → motivo `play failed: <prima riga>` ed esce con il verdetto FAIL (return 1). Il testo di un play riuscito non è stato letto (`bm_net.py` stampa "N bytes in X s ..."): `non verificato` oltre ai tre casi di rifiuto noti.
   3. `n = int(minutes * 60 // every)` controlli: per ciascuno `sleep(every)`, `ask("status")`, conta `up` se la risposta inizia con `status: up`, altrimenti `down` (anche `refused`/`timeout:`). Un `down` NON interrompe la sessione (si conta e si continua), ma il verdetto sarà FAIL. Progresso su stderr (`soak: check i/n up|down`), non su stdout. Un `n` di 0 (minutes troppo piccolo per `every`) è un errore d'uso: `return 2` con "minutes must be at least one --every".
   4. `k = ask("keys monitor")`. Se `k` contiene `back to the menu first` o inizia con `refused` → motivo `cannot end the game from the PC: <prima riga>` (FAIL, si salta il resto). Altrimenti cerca `FPS_LINE.findall(k)`: l'ULTIMA corrispondenza è `title, frames, fps, dropped`.
   5. Solo con `--reboot`: `ask("line reboot")` (se inizia con `refused` → FAIL `reboot refused`); poi fino a `WAIT_REBOOT // POLL_REBOOT` volte: `sleep(POLL_REBOOT)`, `st = ask("status")`; ferma al primo `status: up`. Se non torna su: FAIL `no answer 180 s after the reboot`. Se torna: `prev` = il testo dopo `previous run: ` nella stessa risposta; poi `l = ask("logs lastrun")`; se al passo 4 non c'era una riga dei fps e in `l` ce n'è una, quella (l'ultima) è la riga dei fps.
   6. Verdetto (liste di motivi): `down > 0` → `n status down`; nessuna riga dei fps → `fps line missing`; `fps < min_fps` → `fps X.Y below N` (uguale alla soglia PASSA: `>=`); con `--reboot`: `prev` mancante → `previous run unknown`, e `not prev.startswith("ended cleanly")` → `previous run: <prev>`; senza `--reboot` il campo è `not checked`.
   7. Esattamente 3 righe su stdout, prefisso `soak: `:
      `soak: <file> <M> min, <n> checks, up <u> down <d>`
      `soak: "<title>" <frames> frames, <fps> fps (min <min>), <dropped> dropped` (oppure `soak: no fps line`)
      `soak: previous run <prev | not checked>; verdict OK` oppure `...; verdict FAIL (<motivi separati da "; ">)`
      Exit code: 0 (OK) / 1 (FAIL) / 2 (uso o bridge non raggiungibile) / 3 (il Pi non risponde all'inizio).
