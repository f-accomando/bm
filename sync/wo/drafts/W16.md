## Change (no open design choices)
1. Layout in sets: `#define SET_SIZE 0x180000`; set `s` (0 or 1) lives at `SET_BASE(s) = 0x80000 + s * SET_SIZE` and holds, at these offsets inside it: tables and descriptors (what is at `0x4000..0x50000` today) at `+0x00000`, vertex arrays `+0x10000`, positions `+0x20000`, push `+0x30000`, per-draw blocks `+0x40000`, the heap `+0x80000` (size `HEAP_SIZE` becomes `0x80000`, 512 KiB: say in the report whether the one-triangle probe and a 1024-triangle frame fit; the heap is a guess already), the surface `+0x100000` (up to 0x80000 bytes = 368 x 368 x 4 rounded: refuse larger surfaces for the queue). The GPU page tables stay at `0x0000..0x3000`; the shader code (`BM_VS`, `BM_VS3`, `BM_FS`) lives in the set too (`+0x08000` `BM_VS`, `+0x08100` `BM_VS3`, `+0x08200` `BM_FS`, 128-aligned) and is copied into each set when the set is built. `frame_build` takes the set base as an argument; `mali_frame` (synchronous) uses set 0 and keeps its behavior; `triangle()` and `mali_square` stay where they are. W13a's `mali_backend_flush` surface moves from `0x200000` to set 0's surface (`SET_BASE(0) + 0x100000`) when the page fits 368 x 368, else it keeps `0x200000` (then no frame is in flight: the backend is synchronous).
2. `src/rgb30/mali.h`:
```
/* M41 phase 4: frames in flight. Two sets: a frame is built in the free one while the other may still be drawing.
 * mali_frame_submit takes the same arguments as mali_frame, except the surface: it is the set's own (368 x 368 at most,
 * returned in *surface/*pa/*pitch for the caller to read after the wait). 0 submitted, -1 refused (both sets busy,
 * a bad argument, the surface too big: use mali_frame), -2 failed to start. */
int mali_frame_submit(const mali_hw_t *hw, uint32_t w, uint32_t h, uint32_t clear, const mali_draw_t *draws,
                      uint32_t ndraws, uint8_t **surface, uint32_t *pitch);
int mali_frame_busy(void);                      /* frames still drawing (0..2); advances the state machine (polls the slots) */
int mali_frame_wait(uint32_t timeout_us);       /* until none is: 0, -1 timeout or a job fault (the registers are in the log) */
```
3. `src/rgb30/mali.c`: a small state machine per set (`IDLE`, `VT` = vertex+tiler running on slot 1, `FRAG` = the fragment job running on slot 0, `DONE`): `mali_frame_submit` builds the frame in the free set (`IDLE` or `DONE`), starts the chain on slot 1 (the start half of `run_on`: split `run_on` into `job_start(js, head)` and `job_poll(js, &status)` plus the existing blocking `run_on` made of the two) and sets `VT`; `mali_frame_busy` polls: `VT` and slot 1 ended -> check the status, start the fragment job (`job_fragment` already built) on slot 0, `FRAG`; `FRAG` and slot 0 ended -> `DONE`; a fault -> `DONE` with an `error` flag (logged once with `mali_exception`); returns the number of sets in `VT`/`FRAG`. Only one set may use a slot at a time: if set 0 is in `FRAG` (slot 0) and set 1 reaches the end of its `VT`, set 1 waits in `VT_DONE` (its fragment job starts when slot 0 is free: `mali_frame_busy` starts it then). `mali_frame_wait` loops `mali_frame_busy` until 0 with `H->us()` for the timeout.
4. `tests/rgb30/mali_test.c`: `test_async()` after W12's tests, on the simulator (the simulator faults vertex and tiler jobs, so add to it a flag `S.accept_vt` that makes `run_chain` treat the job types 4 and 5 as no-ops that complete, a few lines in the type test of `run_chain`, `tests/rgb30/mali_test.c:226`); CHECK: (a) submit two frames, `mali_frame_busy() == 2` right after the second submit if the simulator's completion is held back by a flag `S.hold` (new, default 0: while set, `run_chain` leaves `js_status` busy; the test releases it with `S.hold = 0` and a manual `run_chain` call), then after the release `mali_frame_wait(1000000) == 0` and `S.frags_run` rose by 2; (b) a third submit while both sets are busy returns -1; (c) a surface of 400 x 400 returns -1 (too big for a set); (d) the two sets' surfaces differ (`surface0 != surface1`) and sit at `SET_BASE(s) + 0x100000`; (e) a faulting job (the existing `S.bad_job_type_bit` or a forced fault) makes `mali_frame_wait` return -1 and the next submit works again.

## Open decisions (for SPV before assigning)
1. Memory budget: 2 sets of 1.5 MiB + 0.5 MiB shared = 3.5 MiB of the 4 MiB `hw->mem_size`; 720 x 720 surfaces (2 MiB each) do not fit a set: those frames stay synchronous (`mali_frame`, surface at `0x200000`, which is set 1's base: safe only because the backend is synchronous; whether to ask for a larger GPU memory block in `plat.h` for the optional 720 x 720 mode is open).
