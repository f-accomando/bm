# R-NET7 - FB-CRC: comando monitor `crc` e `bm_net --crc` (bozza, NON assegnata)
Origine: proposta PI-SHOT di AGX (Log 16 ott 14:20), riformulata. Assegnatario previsto: NET, dopo R-NET6 (stessi file di rete). Prova hardware: utente (kernel nuovo sul Pi).
Obiettivo: un operatore verifica da solo, via rete, che lo schermo del Pi mostri il frame atteso: CRC32 del framebuffer mostrato, anche fuori da un gioco (menu, monitor), senza scaricare pixel.
Perimetro (righe da riaprire con git grep prima di toccare): `src/kernel/monitor.c` (help_text, `line_command`, elenco comandi a `:291`), `tools/bm_net.py` (opzioni `--crc`, `--crc-expect`), `tools/pi_bridge.py` (`LINE_CMDS` di R-NET6: aggiungere `crc`), `tests/net/check_bm_net_config.py`, `docs/design/pi-test.md`.
NON toccare: `src/net/netcon.c`, `src/net/netxfer.c`, driver fb, `src/lib/crc32.*`, le altre operazioni del bridge.
Decisioni da fissare col planner: D1 CRC della pagina mostrata (`fb->shown`) o di tutte; D2 formato riga `crc: WxH bpp pitch=.. crc32=0x........`; D3 `--crc-expect` con exit 1 su mismatch; D4 il riferimento si prende dallo stesso Pi (golden file in `tests/golden/pi/`, nessun valore inventato); D5 come si tiene fermo il frame (timer/animazioni cambiano il CRC: usare schermata statica, es. menu fermo).
Verifica host: `python3 tests/net/check_bm_net_config.py` con mock; verifica QEMU: comando `crc` risponde nel monitor (test dedicato `-k monitor_crc`). Prova utente: `pi.py line crc` su Pi 1 e RGB30 (RGB30 solo se il kernel lo supporta), due volte sulla stessa schermata statica = stesso CRC.
